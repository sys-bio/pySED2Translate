# viva-tellurium and viva-copasi: the UTC steps are not idempotent

Repositories: viva-tellurium, viva-copasi (0.1.2).  Evidence: **confirmed by running.**

## Summary
A process-bigraph Step may fire more than once (when an input path is updated, and once at the start of a run even with
`run_steps_on_init: false`).  `TelluriumUTCStep` and `CopasiUTCStep` keep their simulator instance between firings and
continue from the previous end state, so each firing returns a different trajectory.

## Reproduction
```python
from process_bigraph import allocate_core
from viva_tellurium.processes import TelluriumUTCStep
from viva_copasi.processes import CopasiUTCStep
core = allocate_core()
ant = "model d; S=1; k=0.5; J: S -> ; k*S; end"
st = TelluriumUTCStep({'model': ant, 'end_time': 5.0, 'n_points': 2}, core=core)
print(st.update({})['species_trajectories']['S'][-1], st.update({})['species_trajectories']['S'][-1])
# 0.08208524272759375 0.006737987073647551   (the second is the state after t = 10)
st = CopasiUTCStep({'model_source': 'decay.xml', 'time': 5.0, 'n_points': 2}, core=core)
print(st.update({'species_counts': {}})['result']['values'][-1], st.update({'species_counts': {}})['result']['values'][-1])
# [0.0820849...] [0.0067379...]
```

## Expected
Either reset to the configured initial state at the start of each `update()` (so a Step is a pure function of its
inputs), or say in the documentation that these steps are stateful and must fire exactly once.

## Why it matters
Step firing counts are an implementation detail of the scheduler; a document whose result depends on how often a step
fires is hard to reason about.

Environment: Python 3.13, process-bigraph 1.8.5, bigraph-schema 1.7.0, numpy 2.2.6; Linux (x86_64). Observed 2026-10-09.
